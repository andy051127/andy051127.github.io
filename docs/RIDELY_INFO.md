# Ridely (라이들리) — 프로젝트 정보

> 포트폴리오 작성용 정리 문서. 코드·`docs/shared/`의 스파이크 기록·커밋 이력에서 확인되는 사실만 담았다.
> `[채우기]` 표시는 저장소만으로는 알 수 없는 항목(본인 역할, 수상 결과, 배포 URL 등)이라 직접 채워야 한다.

---

## 1. 한 줄 소개

**흩어진 자전거 인프라를 활용해 라이딩을 키우는 AI 트레이너.**
한국관광공사 관광 데이터(TourAPI)와 자전거 공공데이터(급수대·수리소·따릉이·사고다발지)를 통합하고, AI 코치 **"Coach Ridely"** 가 라이더의 목적(편의·운동·풍경)에 맞춰 한강 자전거길 코스를 설계하고 코칭하는 모바일 앱.

| 항목 | 내용 |
|---|---|
| 출품 | 2026 관광데이터 활용 공모전 (한국관광공사) — 웹·앱 개발 부문 |
| 서비스 범위 | 한강 자전거길 서울 구간 (아라한강갑문 ~ 잠실, 약 40km) |
| 형태 | Android 앱 (Cordova) + Spring Boot 백엔드 |
| 개발 기간 | 2026-07 ~ (첫 커밋 2026-07-08, 총 400여 커밋) |
| 팀 | 5~6인 규모 (커밋 작성자 기준) · 본인 역할: `[채우기]` |
| 링크 | 배포 URL / 시연 영상 / 앱 스토어: `[채우기]` |

---

## 2. 해결하려는 문제

- 자전거 라이더에게 필요한 정보(급수대, 수리소, 따릉이, 위험 구간, 주변 관광지)가 **기관별·서비스별로 흩어져** 있어 코스를 짜려면 여러 앱을 오가야 한다.
- 기존 경로 앱은 "최단/최적 경로"는 주지만, **"오늘 12km쯤, 풍경 위주로, 중간에 물 마실 곳 있게"** 같은 목적 기반 코스는 만들어주지 않는다.
- 라이더 안전(사고다발지)과 관광(주변 명소)을 한 경로 안에서 같이 다루는 서비스가 드물다.

## 3. 주요 기능

| 기능 | 설명 |
|---|---|
| **AI 코스 설계** | 출발지·도착지·목표 거리·우선순위(편의/운동/풍경, 가중치 합 1)를 입력하면 인프라·관광지가 자연스럽게 경유되는 코스를 생성 |
| **Coach Ridely 코멘트** | 코스에 대한 코칭 문장, 위험 구역 안내, "다음엔 +2km 어때요?" 식의 다음 단계 제안 |
| **경로 시각화** | 지도 위 경로 + 인프라 5종 마커 + 사고다발지 3등급 표시, 경유지 탭 시 바텀시트로 상세(사진 포함) |
| **내 주변 인프라** | 폰 안에서 GPS로 반경 필터링 (서버에 위치 미전송, 6장 참고) |
| **라이딩 모드** | 실시간 추적, 사고다발지·코스 내 관광지(200m) 근접 안내 — 전부 기기 내 계산 |
| **저장 경로 / 라이딩 이력** | 저장 경로 CRUD, 누적 거리·횟수 통계 (이력은 기기 `localStorage`) |
| **회원** | 회원가입/로그인(JWT), 비로그인 상태에서도 코스 추천·장소 검색 체험 가능 |

## 5. 아키텍처

### 5.1 계층 구조

```
Controller → Service(interface + Impl) → DAO(MyBatis Mapper / JdbcClient raw SQL)
                         │
                         └─ infra/{llm, ors, kakao, taas, seoul, tourapi, seed}  외부 연동
```

- 모든 응답은 `ApiResponse<T>` 봉투(`success / data / error`)로 통일, 예외는 `BusinessException + ErrorCode`를 `GlobalExceptionHandler`가 변환.
- 인증은 stateless JWT(액세스 15분, 리프레시 DB 회전). 비로그인 허용 경로는 `SecurityConfig.PUBLIC_PATHS` 한 곳에서 명시 관리.

### 5.2 인프라 구성 (Terraform)

```
Android 앱 / 웹 ──► CloudFront ──► EC2 (Spring Boot, systemd) ──► RDS PostgreSQL(PostGIS)
                                      │
                                      ├─► LLM  (Bedrock · LiteLLM 게이트웨이 · Gemini)
                                      └─► ORS · Kakao · TourAPI · TAAS · 서울 열린데이터
```

- EC2는 **Instance Role**로 AWS에 접근 — 정적 AWS 키가 어디에도 없음.
- 시크릿은 EC2의 `.env`에만 존재, 저장소에는 없음 (게이트웨이 주소·키 포함).

## 6. 핵심 설계 포인트 / 기술적 의사결정

> 포트폴리오의 중심이 될 부분. 각 항목은 코드 주석과 `docs/shared/`에 근거가 남아 있다.

### 6.1 코스 추천 파이프라인 (`RouteRecommendServiceImpl`)

```
검증 → 멱등성 재생 → 후보 수집 → LLM 코스 설계 → ORS 경로 산출(+거리 보정) → 코치 코멘트 → 응답/저장
```

1. **검증** — 우선순위 가중치 합=1, 서비스 지역(bounding box) 내부, 목표 거리가 직선거리 대비 물리적으로 도달 가능한지.
2. **멱등성** — `Idempotency-Key`로 20분간 응답 재생. **검증 이후**에 확인해 잘못된 요청이 키를 소모하지 않게 함.
3. **후보 수집** — PostGIS로 목표 거리에서 유도한 반경 내 인프라·관광지 수집.
4. **코스 설계** — LLM이 후보 ID 중에서 경유지를 선택. 응답의 ID가 후보에 없으면(환각) 재시도 후 규칙 기반 `FallbackCourseDesigner`로 대체.
5. **경로 산출** — OpenRouteService로 실제 도로 형상 생성. 사고다발지 회피를 한 번 시도하고, 회피 때문에 경로가 불가능해지면 회피 없이 재시도.
6. **코멘트** — LLM 코멘트, 실패/톤 위반 시 `TemplateCommentFactory` 템플릿으로 대체.
7. 둘 중 하나라도 폴백이면 `aiProvider="FALLBACK"`으로 표시 — **규칙 기반 결과를 AI 결과로 속이지 않음.**

### 6.2 "목표 거리 맞추기" — 4번 실패 후 방법을 바꾼 사례 (`SPIKE_TARGET_DISTANCE.md`)

- **문제**: 목표 12km인데 경로가 6~7km(목표의 51~65%)로 나옴.
- **시도 4건**(후보 정렬 교차, 후보 상한 해제, 축 이탈 후보 제거 등)은 모두 실패. 후보 품질과 실측 거리 사이에 **상관이 없음**을 데이터로 확인.
- **원인 재정의**: "자연스러운 코스"와 "목표 거리 채우기"는 서로 다른 목표 → LLM이 경로에 붙은 지점을 고르는 건 *옳은 판단*이었음.
- **해결**: 거리 책임을 LLM 설계 단계에서 빼고 **서비스 단계로 이동**. 1차 측정 후 목표의 90% 미만이면, 자전거도로 위에서 도착지 반대편으로 나갔다 오는 연장점을 PostGIS(`ST_DumpPoints`)로 찾아 경로 앞에 삽입. 한 번만 보정(수렴 루프 없음), 서비스 지역 밖 제외·악화 시 되돌리기 가드레일 포함.
- **결과**: 4개 케이스 중 3개에서 오차 +3.2 ~ +6.6%.
- 프롬프트 튜닝으로 풀리지 않는 문제를 데이터로 판별하고 구조를 바꾼 경험.

### 6.3 위치정보 서버 무전송 원칙 (`LOCATION_PRIVACY_ARCHITECTURE.md`)

- **원칙**: 기기 GPS로 얻은 값은 원본·가공값(거리·속도·궤적) 모두 서버로 보내지 않음 — 위치정보법 상 개인위치정보 수집 여지를 구조적으로 차단.
- **구현**: "내 주변 인프라"는 서버에 위치를 보내는 대신 `GET /pois/all`(파라미터 없음)로 전체 목록을 받아 **폰에서 GPS로 필터링**. 라이딩 기록은 `localStorage`에만 저장하며 서버 호출 자체를 제거.
- **계약 테스트**: `PoiAllTest`가 "위치 파라미터를 붙여도 응답이 동일"함을 고정해, 나중에 누가 좌표 파라미터를 추가해도 깨지게 함.
- **성능**: 전체 응답을 slim하게 유지, 서버 메모리 캐시, **weak ETag**(strong ETag는 Tomcat gzip을 조용히 꺼버림) — 전체 조회 크기를 실측해 문서화.
- 법률 자문 확인 후 "프론트에서만 처리되면 문제없다"는 범위 내에서 설계.

### 6.4 LLM 공급자 추상화와 운영 대응

- 같은 `ChatClient` 코드로 **Gemini(로컬) / Bedrock Claude(운영) / LiteLLM 게이트웨이(OpenAI 호환)** 전환 — 환경변수 `LLM_PROVIDER` 하나로 결정.
- 운영 중 Bedrock 직접 권한이 회수될 일정이 생겨, **코드 변경 없이** 게이트웨이로 전환할 수 있게 공급자를 추가함. 이때 OpenAI 스타터가 끌고 오는 임베딩·이미지·음성 자동설정이 키를 요구하는 문제를 설정으로 차단.
- 서비스 전체 일일 LLM 호출 상한(`LlmCallBudget`)으로 무료 쿼터 보호.
- 실패 모드 전반에 폴백: 호출 실패 / 환각 ID / 톤 위반 → 규칙 기반 또는 템플릿.

### 6.5 "검증하고 폐기한" 설계들 (데이터 기반 의사결정)

| 사례 | 결정 | 근거 |
|---|---|---|
| **고도(누적 상승) 보정** | 보정하지 않고 강도 판정에서 고도를 제외 | 6개 구간 실측: 평지에서 ORS 고도가 3~4배 과대 계상. 경사 상한 보정은 실제 오르막(남산 236m→12.9m)을 파괴, 공개 DEM은 SRTM보다 나쁨 → 방법 자체를 반증 |
| **두루누비 API** | 채택 안 함 | 코스 144건이 전부 걷기 코스, 자전거 0건 (`SPIKE_DURUNUBI.md`) |
| **노선 형상 대체 소스 4곳** | 모두 부적합 판정 후 탐색 종료 | WMS는 이미지라 좌표 추출 불가 등. 같은 곳을 다시 파지 않도록 `DATA_SOURCES.md`에 기록 |
| **톤 검증 후 재호출** | 재호출 없이 템플릿 직행 | 운영 코멘트 46건 전수 검사에서 위반 0건 → 빈도 낮은 문제에 LLM 재호출 비용을 쓰지 않음(단, "0건≠없음, 상한 약 6%"로 한계 명시) |
| **위험 안내 검사 → 관측으로 후퇴** | 검사 로직 대신 로그만 | 정탐 0·오탐 1이었고, 위치 전달은 지도/GPS 알림이 결정론적으로 담당하므로 LLM 문장을 근거처럼 다룬 게 잘못된 층이었음 |

### 6.6 데이터 파이프라인과 공간 DB

- 5개 이상 공공데이터를 적재·정규화 (TourAPI 710건, 자전거길 13노선/1,024, 서울 자전거 편의시설 1,100, 따릉이 대여소 3,239, 사고다발지 111건 등).
- 소스가 바뀌어도 재적재가 안전하도록 **자연키 기반 멱등 적재**(예: 수리소 natural key 마이그레이션).
- 사고다발지는 폴리곤(MultiPolygon)으로 저장, 위험 등급별 회피 대상 선정 기준을 `application.yml`에 근거와 함께 기록.
- PostGIS 활용: 반경 검색, 선분까지 거리·진행도 계산, `ST_MakeEnvelope`로 서비스 지역 제한, 경로 위 점 샘플링.

### 6.7 품질·운영 프로세스

- **Flyway 도입 계기**: schema.sql만 고치고 DB에 반영하지 않아 사고가 2번 발생(그중 하나는 6일간 잠복) → 마이그레이션 자동화. 테스트도 같은 마이그레이션을 타도록 해 "테스트는 통과, 개발은 실패"를 제거.
- **CI**: PR마다 Testcontainers 기반 통합 테스트, main 브랜치 보호 규칙으로 직접 push 차단. 배포는 보호된 main 병합에서만.
- **보안 점검**: 외부 문자열 `innerHTML` 삽입 XSS 차단, CSP(Kakao SDK 허용), 테스트 전용 의존성 CVE 오버라이드(commons-compress/lang3), 토큰 해시 저장.
- 코드 주석에 **"왜 이렇게 했는가·무엇을 시도해 버렸는가"** 를 남기는 규칙을 팀 컨벤션으로 운영.

| 국문 관광정보 서비스 (TourAPI, `KorService2`) | 한국관광공사 | 관광지·사진·상세 정보 (**공모전 필수 요건**) |
| 자전거길 DB | 행정안전부 | 국토종주 노선 형상, 급수대·인증센터 등 시설 |
| 서울시 자전거 편의시설 | 서울특별시 | 공기주입기, 수리소 |
| 서울시 공공자전거 대여소 | 서울특별시 | 따릉이 대여소 |
| 자전거 교통사고 다발지역 | 도로교통공단(TAAS) | 위험 구역 폴리곤, 회피 라우팅 |
| OpenRouteService / Kakao Local | 외부 서비스 | 경로 생성 / 장소 검색 |

채택·미채택 판단과 이용허락 근거는 `docs/shared/DATA_SOURCES.md`에 정리.

## 9. 포트폴리오에 쓸 수 있는 어필 포인트

1. **LLM을 믿지 않는 설계** — 환각 ID 검증, 재시도 정책, 규칙 기반 폴백, 톤 검증, 호출 예산, 폴백 시 AI 표시 정직성.
2. **프롬프트가 아니라 구조로 푼 문제** — 거리 보정 4회 실패 → 원인 재정의 → 서비스 단계 보정으로 이전 (오차 ±5%대).
3. **데이터로 반증하고 접는 판단력** — 고도 보정·두루누비·톤 재호출 등 "하지 않기로 한 결정"을 근거와 함께 기록.
4. **개인정보/법적 제약을 아키텍처로 해결** — 위치정보 서버 무전송 + 계약 테스트로 고정.
5. **공간 데이터 처리** — PostGIS 기반 후보 수집, 회피 라우팅, 경로 위 연장점 탐색.
6. **풀스택 + 인프라 + 배포 자동화** — Spring Boot / 바닐라 JS / Cordova APK / Terraform(AWS) / GitHub Actions.
7. **운영 현실 대응** — LLM 공급자 권한 회수 일정에 맞춰 코드 변경 없이 전환 가능하게 한 사례.
